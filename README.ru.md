# srt: обратные SSH-туннели на VPS

`srt` открывает туннели **с машины без входящего доступа** (за NAT или прокси, который пускает только CONNECT) **на VPS**, чтобы к машине можно было подключиться откуда угодно через VPS. Туннель поднимает сама машина; ничего другого в цепочке запускать не нужно.

```
 вы ──ssh -p 2222──▶ VPS:2222 ══ обратный туннель ══▶ эта машина ─┬─▶ 127.0.0.1:22        (сама машина)
                                 (поднят srt)                      └─▶ 10.0.0.5:80         (хост в LAN)
```

- На одной машине можно держать несколько туннелей: к разным VPS, на разные порты и к другим хостам локальной сети, а не только к себе.
- Исходящий SSH может идти через HTTP CONNECT-прокси (например, такой, который перехватывает TLS).
- Каждый туннель — отдельный сервис: он перезапускается сам и переживает перезагрузку (см. примечание для Linux).

## Установка

Одной строкой (нужны `curl` или `wget`, а также `sudo` для системных пакетов, если вы не root):

```sh
curl -fsSL https://raw.githubusercontent.com/vkust/ssh-reverse-tunnel/main/install.sh | sh
```

Нет `curl`? Используйте `wget -qO- https://raw.githubusercontent.com/vkust/ssh-reverse-tunnel/main/install.sh | sh`.

Установщик скачивает исходники, определяет систему, ставит ssh и python3 и запускает мастер для первого туннеля. Ответы читаются из терминала, поэтому пайп не мешает вопросам.

Из клонированного репозитория:
```sh
git clone https://github.com/vkust/ssh-reverse-tunnel && cd ssh-reverse-tunnel
sh install.sh            # с вопросами
```

Без вопросов:
```sh
curl -fsSL https://raw.githubusercontent.com/vkust/ssh-reverse-tunnel/main/install.sh | sh -s -- -y --vps 192.0.2.10 --proxy proxy.example.com:3128
```

`install.sh` определяет формат пакетов и архитектуру и использует подходящий менеджер:

| Формат | Системы | Менеджер пакетов |
|---|---|---|
| deb | Debian, Ubuntu | apt-get |
| rpm | Fedora, RHEL, openSUSE | dnf / yum / zypper |
| pacman | Arch | pacman |
| apk | Alpine, OpenWrt 24+ | apk |
| ipk | OpenWrt (opkg) | opkg |
| brew | macOS | Homebrew |

Проверить, что система определилась правильно: `srt platform`.

Нативный Windows не поддерживается. Запускайте `srt` в WSL2 или на той машине, которая реально держит соединение.

## Управление туннелями

```sh
srt add                         # мастер: имя, VPS, прокси, целевой хост:порт, порт на VPS, ключ
srt add --name nas --vps 192.0.2.10 --target 10.0.0.5 --target-port 80 --remote-port 8080 -y
srt list                        # все туннели и их состояние
srt show nas
srt check [nas|all]             # вход на VPS по ключу, слушает ли порт на VPS, состояние сервиса
srt restart nas                 # start | stop | restart | status  [NAME|all]
srt logs nas -f
srt key nas                     # публичный ключ, который нужно положить на VPS
srt remove nas [--purge-key]
srt uninstall                   # удалить все туннели и сервисы
```

Каждый туннель хранится в `~/.config/srt/tunnels/NAME.conf`. Имя — это ручка для всех команд. Один порт на VPS может использовать только один туннель; `srt add` отказывает при совпадении.

### Что означает цель

- `--target 127.0.0.1` (по умолчанию): собственный порт этой машины, например sshd на 22.
- `--target 10.0.0.5`: хост локальной сети, доступный с этой машины. Трафик идёт VPS → туннель → эта машина → этот хост. Хосту в LAN знать о туннеле не нужно.

## Настройка VPS

Выполните один раз на VPS от root:
```sh
sudo srt setup-vps
```
Команда ставит `GatewayPorts clientspecified` (чтобы туннели могли слушать публичный адрес), проверяет конфиг sshd и перезапускает его. Откройте порты туннелей в файрволе (`ufw allow 2222/tcp`). На VPS `srt` нужен только если вы хотите использовать эту команду; сам туннель работает и без него.

## Ключи и доступ

- `srt add` создаёт ed25519-ключ без пароля для каждого VPS (`~/.ssh/srt_<host>`), потому что сервисы запускаются без участия человека.
- Если вход по ключу не работает, `srt add` один раз предложит `ssh-copy-id`.
- **Любой, кто может подключиться к `VPS:PORT`, получит приглашение входа sshd на целевой машине.** Отключите парольный вход на целевой машине и ограничьте порт известными адресами на файрволе VPS.

## Примечание для Linux: запуск при загрузке

Туннели — это пользовательские сервисы systemd (`srt@NAME.service`). Без linger они останавливаются при выходе из системы и не запускаются при загрузке. Если linger выключен, `srt add` выводит команду для его включения:
```sh
sudo loginctl enable-linger $USER
```

| `.github/workflows/ci.yml` | юнит-тесты, shellcheck, цикл установка → добавление → удаление → деинсталляция |

## Решение проблем

- `Permission denied (publickey)`: выполните `srt key NAME` и положите ключ на VPS для пользователя туннеля.
- `remote port forwarding failed`: на VPS выключен `GatewayPorts` (`sudo srt setup-vps`) или порт занят.
- `proxy refused CONNECT`: прокси не разрешает подключение на этот порт. Проверка: `curl -x http://PROXY -v telnet://HOST:22`.
- `srt check` говорит, что VPS слушает порт, но туннель не запущен: порт занят другим туннелем или процессом.

## Удаление

```sh
srt uninstall && sh install.sh --uninstall
```
Ключи `~/.ssh/srt_*` сохраняются; удалите их вручную, если они не нужны.
